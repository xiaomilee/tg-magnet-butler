# 更新日志

> 这份是完整历史。`manifest` 里的 `changelog` 只保留最近两版摘要——
> 飞牛应用中心对 manifest 单个字段的长度有上限，逐版累加会让安装包被拒
> （1.0.12 起覆盖安装失败就是这个原因，详见 1.0.15）。

## 1.0.42

**修「迅雷又连不上了」的真根因：那句 `invalid token` 是飞牛网关说的，不是迅雷云。**

真机现场（2026-11-14）：迅雷一直登录着、没退出过，`pan_auth` 的 `exp` 还写着 2 天后到期，
程序却一直 `invalid token`。1.0.41 把它判成「`pan_auth` 被云端作废」，方向是错的。

逐项剥离后真相很朴素——新版飞牛（迅雷套件 3.23.5 起）改认 Cookie 里的
`fnwg_token` + `ost`，而**只要 Cookie 里出现 `fnos-token` 这个名字，网关就整条拒**，
值和位置都不看（回 13 字节纯文本 `invalid token`，HTTP 还是 200）：

| Cookie 组合 | 结果 |
| --- | --- |
| `fnwg_token` + `ost` | ✅ 200，任务列表正常 |
| 上面再加 `fnos-token`（放前/放后） | ❌ `invalid token` |
| 只有 `fnwg_token` / 只有老 `fnos-token` | ❌ `invalid token` |

最硬的一条对照：把浏览器里能用的那条 URL 原样从外部请求，去掉 Cookie 立刻 `invalid token`。
所以「带不带 fnos-token 回答一模一样」只能推出「这个 Cookie 没被接受」，推不出「问题在 pan_auth」。

改动：

- 新增 `download.xunlei.fnos_cookie`，存整条 Cookie；`util.clean_fnos_cookie()` 负责去掉
  `Cookie:` 前缀与引号、处理多行粘贴、**在有 `fnwg_token` 时把 `fnos-token` 整项剔掉**。
  老的 `fnos_token` 保留给没升级的飞牛，两者都在时以 `fnos_cookie` 为准，绝不再把它拼进 Cookie。
- `_headers()` 改成「有整条 Cookie 就原样发」，不再固定拼 `fnos-token=`；自定义头只在走老路时补。
- `auth_culprit()` 换判据：拿 `<网关>/` **套件首页**当探针——那个页面不需要 `pan_auth`，
  打得开就说明登录 Cookie 是好的。不再拿两个任务列表回复做比较。
- **自动换令牌**：首页 HTML 里内联着 `uiauth(value){ return "eyJ…" }`，`fetch_pan_auth()`
  把它读出来；探测到 `invalid token` 且探针能打开时，自动换上新令牌重试一次，成功后落盘。
  这也让 `rescan_xunlei_token()` 从「扫目录」改成「先问首页」——新版套件根本不落盘，
  1.0.41 那句「本机没扫到能用的令牌」就是这么来的。
- 面板取登录态的路径同步扩容：`note_fnos_token()` 除了 `fnos-token`，也认
  `fnwg_token` / `ost` / `osrt` / `xtoken` / `xla_ci`，用户打开一次面板就自动存下整条。
- 设置页那一格改名「飞牛登录 Cookie」，说明改成「F12 → Network → 复制 `Cookie:` 整行粘进来」。
- 1.0.41 的救急写法（把 `fnwg_token` / `ost` 塞在 `xla_ci` 里）由 `_migrate_xunlei()` 自动拆开：
  `xla_ci` 还原成纯值，其余搬进 `fnos_cookie`，升级后不用手改配置。
- 测试：新增 `tests/test_fnos_cookie.py`（16 项，清洗/剔除/首页取令牌/失败重试/配置迁移），
  重写归因与 header 用例；总数 510 → **529**。

## 1.0.41

**修「迅雷又连不上了」：pan_auth 被粘成了整条 watch 地址。**

真机现场（2026-11-14）面板报连不上，`probe` 回来的是：

```
permission_deny: checkAuth failed:
token contains an invalid number of segments
token:http://192.168.1.2:5666/cgi/ThirdParty/xunlei/index.cgi/device/info/watch
      ?pan_auth=eyJhbGciOi…&device_space=&space=device_id%231fef9844
```

这句「segments 不对」看着像令牌过期，其实是**形状**不对：配置里那串 `pan_auth`
不是 JWT，而是从浏览器 F12 里连地址一起复制下来的整条 `device/info/watch` URL。
网关把这一整串当 token 转给迅雷云，云当然认不出来。同一台机器、同一份 fnos-token，
把里面那段 JWT 掐出来之后立刻就通了（`✔ 已拿到设备空间`，令牌还剩 2 天）。

- `util.clean_pan_auth()`：能认整条地址、`pan_auth%3D…` 编码形式、`"pan_auth":"…"` 片段、
  带 `Bearer ` 前缀的写法；认不出形状就**原样返回**，不猜、不截断。
- 三个入口都校一遍：**读配置**（`Config.load` 里修好并落盘，下次启动不会又变回地址）、
  **存配置**（`apply_patch`，面板上贴完一保存就归位）、**发请求**（`XunleiDownloader.__init__`，
  防住别处塞进来的脏值）。
- `xunlei_detect` 抓到的候选与写回的 `patch_for` 也走同一条清理。
- 提示别再把人带偏：形状不对时直说「不是 JWT，只要 `pan_auth=` 后面那一段」，
  不再劝你重登飞牛；网关 403 且配置里有令牌时改说「这串多半过期了」，
  而不是「缺 fnos-token」——手里明明有。
- 设置页 `pan_auth` 一格补了说明：粘整条地址也没关系，保存时自动掐出那段。

测试：新增 `tests/test_token_shape.py` 12 项（清理的六种输入、读配置落盘、保存时修复、
脱敏回写不误伤、构造请求时兜底、提示文案、`patch_for` 只写 JWT），全量 510 项通过。

## 1.0.40

**代理不再分主备：一个框，一行一个地址。**

以前「主代理」在 Telegram 卡、「检索站单独的代理」在站点卡、「备用通道」单开一张表，
同一台 Clash 要填两遍，还看不出「先试谁」。现在只剩设置页一张「代理」卡：

- **一个多行输入框**，一行一个地址，从上往下试；这条不通自动换下一条，全都不通才走直连；
  一行都不填就是直连。框下面按行号列出每条的实测结果（`✓ 24 ms` / `✗ 连接被拒绝…`），
  不用为了看一眼状态先点一次测速——状态每隔几秒从后端取。
- Telegram 和检索站**共用这一份**。原来的 `nyaa.proxy` 不再单独填；老配置里填过的那个地址
  会自动并进框里（并进第一行之后的某一行），保存一次就归位。
- 内部的 `primary` / `channel` 只是「填在第一行」和「填在后面」的位置称呼，**没有优先级**：
  选路仍然是「在用的那条还通就不换，断了才按你写的顺序挑第一条能通的」，所以谁都能当谁的备胎。
- 面板上的说法全部换成地址（`现在走 192.168.1.11:7890（128 ms）`），不再出现「走主代理」
  「走备份」这类字样；每条的启用开关去掉了——要停用某条，删掉那一行即可
  （老配置里被关掉的线路，保存时仍保持关闭，不会突然复活）。
- 每行结果里顺手把报错压短了：地址左边已经写了，`经代理 http://… 拒绝连接（errno 111）。…`
  这种长句会挤掉结果本身，现在只留「连接被拒绝」，完整原因挂在 title 上。

测试：新增 7 项（`short_name`、状态里列出全部线路、`config_primary` 兼容老 `nyaa.proxy`、
字符串形的线路表、模块级 `status(primary)`），UI 自检 100 项，其中代理段全重写。

## 1.0.39

**测速不再「一票否决」：线路只通一个目标也算能用。**

现场：主代理 `192.168.1.10:7897` 真的没在监听，程序却把唯一能用的备用
`192.168.1.11:7890`（Telegram 8 ms 就通）也判成死线，于是主副全红、落到直连，
本来能跑的投递一起废了。

原因是探测同时要连 `api.telegram.org` 和 `sukebei.nyaa.si`，**要求两个都通**。
而那条 Clash 对 `nyaa.si` / `sukebei.nyaa.si` / `e-hentai.org` / `javdb.com` 一律回
`503 Service Unavailable`（策略组里没有可用节点），于是 Telegram 通、检索站不通 →
整条被判死。

现在的判定：

- **至少一个目标通 = 这条线路可用**，会正常参与「互为备胎」的选路；
- 只通一个的标成琥珀色 `✓ 10 ms · 检索站✗`，并写明是哪个站、什么原因，
  不再画成红色（红色在这个面板里代表「废了」）；
- 两个都不通才算死线，才轮到下一条 / 直连。

健康表里也记下这条 `note`：`/api/status.proxy.items[].note` 会给出
「检索站不通」，`note_detail` 是完整原因；`/api/proxy/test` 多返回
`picked_note` / `picked_note_detail`。

测试：新增 `tests/test_proxychan.py` 4 项（部分可用 / 全灭才算死 / 健康表不冷却 /
部分可用优先于直连）、`tests/test_ui_markup.py` 1 项（琥珀色而不是红色），
全量 **492 项通过**；面板自检 100 项通过。

## 1.0.37

**「迅雷无法投递」最常见的那条：建任务次数达到上限，被错报成了令牌失效。**

现场（HTTP 403）：

```json
{"error":"task_create_count_limit","error_code":11,
 "error_description":"任务创建次数达到上限","HttpStatus":403}
```

旧代码对 401/403 一律按「令牌问题」处理，于是：报错说「迅雷鉴权失败……被拒的是建任务的参数」，
把人往重抓 pan_auth、换目录上带；还顺手做了「改用最简请求体重试」+ 上层「重扫令牌后再投一次」，
同一条磁力对着同一个额度撞了三到四次，额度越用越少。

- 新增 `classify_quota()`：从 `task_create_count_limit` / 「任务创建次数达到上限」/
  `too many requests` 这类文案认出限流；`classify_task_error()` 里**排在鉴权之前**判。
- 403 分支不再无脑挂 `_auth_failed`：限流回 `_quota` 标记，上层不会再去重扫令牌。
- 认出限流就**一次都不重试**（不换目录、不减字段、不重投），日志留一行
  「迅雷建任务被限流，本次不再重试」。
- 文案：说清这是迅雷账号侧的额度（非会员每日任务数上限、短时间连续投递也会撞），
  给出三条出路——等额度恢复、手机迅雷 App 手动加、配 aria2/qBittorrent 兜底。
- 限流挡在「取设备空间」那一步时，也不再报「未取到设备空间，检查 pan_auth」。
- 顺手：**经代理 TLS 握手中断**的提示不再劝人设 `TMB_INSECURE_TLS`（那管的是系统 CA，
  关掉证书校验对「代理把连接关了」毫无用处），改成「换条线路 / 代理里换节点再试」。
- `docs/迅雷接入.md` 故障对照表新增这一条，并补专门一节。

测试：新增 `tests/test_xunlei_quota.py` 8 项（识别、403 分叉、不重试、取空间环节）、
`test_core` 2 项（代理握手中断的文案），全量 **486 项通过**。

## 1.0.36

**主代理和备用通道互为备胎：谁在扛就一直扛，断了才换人。**

1.0.35 是「主代理优先」——主代理只要通了就硬切回去。局域网里两条线其实是一样好的
（比如 NAS 本机的 Clash 和隔壁电脑的 Clash），来回切只会让连接和 TLS 一直重建。

- **选路改成粘性**：自动测速先看「正在用的那条」还通不通，通了就不动它；
  不通才按「主代理 → 备用通道（按你排的顺序）→ 直连」挑第一条能用的。
  于是主代理是备用通道的备胎，备用通道也是主代理的备胎，两个方向都成立。
- **直连不算备胎**：代理全灭落到直连后，代理一恢复就回代理，不会赖在直连上。
- **手动「测速并切换」同一套逻辑**：在用的那条还通就写「正在用「X」（22 ms）」，
  真换了才写「已切到「X」」；第一次还没有走向时写「现在走…」。
- `/api/status` 的 `proxy` 段多给一个 `preferred_name`（选中那条通道的名字），
  面板状态行直接写「走备份 书房PC」，不用再拿地址猜是谁。
- 卡片文案同步：写明「互为备胎」，不再写「顺序固定」。

测试：`test_recovers_back_to_primary` 换成「在用的线还通就不切回」「备用挂了主代理顶上」
「直连不粘」三项，全量 **476 项通过**；面板交互自检 **88 项通过**。

## 1.0.35

**代理设置合并成一张卡：主代理、备用、自动切换都在一处，顺序一眼看得懂。**

以前三处分散：主代理在「Telegram」卡、检索代理在「站点与去重」卡、备用通道单开一张
「代理通道」——改一处得先找它在哪，也看不出「先试谁」。

- **设置页只剩一张「代理」卡**，从上到下就是尝试顺序：
  主代理（Telegram 与检索站共用）→ 检索站单独代理（留空跟随）→ 备用通道 → 自动切换。
- **「测速并切换」**（原来的「测速」）：主代理、每条备用、直连**并行**测，
  严格按上面的顺序挑第一条能用的——备用快 30 ms 也不顶掉主代理。
  每行后面直接写结果，主代理那格和底部的「直连」也各有一行。
  表单有未保存改动时，会先落盘再测，免得选中一条程序还不认识的线路。
- **自动切换**（默认开）：后台每 3 分钟测一次，主代理恢复就切回去、断电就顶到备用通道、
  全不通才走直连。**只改内存里的走向，不动配置**。
- 选中的走向按「哪条主代理」分开记（机器人、检索站各自独立），删掉某条通道后旧走向自动作废。
- 新增 `POST /api/proxy/test`；`/api/status` 的 `proxy` 段改成直接给出当前走向
  （`preferred` / `preferred_kind` / `auto`）。
- 顺手修：直连探测原来对两个目标串行做，一个域名解析慢就能把「测一次」拖到 16 秒；
  现在并行，通常 3–6 秒内出结果。

测试：新增 13 项（选路优先级、主代理恢复切回、全灭落直连、失效走向作废、定时开关落盘等），
全量 **474 项通过**；面板交互自检 **88 项通过**。

## 1.0.34

**多一条代理线路：主代理挂了，程序自己换下一条。**

- **设置页新增「代理通道」**：主代理（`telegram.proxy` / `nyaa.proxy`）之外最多再挂 6 条备用线路，
  最常见的是把开着 Clash 的那台电脑填进来（`http://192.168.1.10:7897`）。
  电脑关机、换端口、节点被墙，都不用再爬上 NAS 改配置。
- **失败真的会换线**：`util.http_request`、`util.http_download`、Telegram 轮询的重试循环里，
  第 N 次重试走第 N 条线路（续传仍带 `Range` 从断点接着要）。刚失败的那条被记 5 分钟并排到队尾，
  免得每次请求都先撞一次墙；主代理恢复后自动回到第一位。
- **主代理留空时通道优先**：只填了通道没填主代理，先走通道、直连垫底，
  不再「先白等一次超时再换」。
- **面板上看得见**：卡片右上角写「正在用 http://…」，指的是最近一次**真的走通**的线路；
  「测速」逐条做 CONNECT 探测，同时试 `api.telegram.org:443` 和 `sukebei.nyaa.si:443`，
  两个都通才算可用，并把结果当场写进状态。
- 新增 `app/tmb/proxychan.py`：地址归一化（没写端口不猜）、去重、上限 6 条、健康记录与降级顺序；
  内网/本机地址依旧永远直连。

实测（同网段的 Clash Verge）：CONNECT 探测 telegram 46 ms、nyaa 19 ms；把该地址填成通道、
主代理留空后，`/api/probe/nyaa` 经这条通道取回 5 条结果，`/api/status` 里 `last_used` 正是它。

测试：新增 **28 项**（含一个真 socket 假代理跑「第一条死、第二条活」的集成用例），
全量 **461 项通过**；面板交互自检 **73 项通过**。

## 1.0.29

**真凶：整棵树被 `list` 和 `dir` 包了两层，而 `dir` 是对象、不是路径。**

1.0.28 的「往里钻」方向没错，但现场一探就发现根本不用钻——**清单就在第一次响应里**，
只是藏在两个对象里。用新增的 `{"probe": …}` 通道把迅雷原话打出来：

```json
{"list_id": "Ah5-…",
 "list": {"page_size": 2000,
          "resources": [{"name": "FC2PPV-5003668", "is_dir": true, "file_count": 6,
                         "dir": {"page_size": 6, "resources": [ …6 个文件… ]}}]}}
```

老代码只认平铺的 `resources` / `list`（数组）：

* `_parse_body` 取到 `list` —— 但它是个**对象**，于是被当成「一个节点」，这个节点恰好有
  `resources`，看着像目录；
* 再往里是那个 `is_dir` 的根目录节点，子项在 **`dir`** 里，而 `dir` 是
  `{"page_size": 6, "resources": […]}`，不是字符串路径 —— `node.get("resources")` 取不到，
  于是「目录没有子项」→ 被 `_flatten_files` 丢掉 → **0 个文件**。

所以：`_resources_of()` 现在会连剥两层（`list` → `resources`，目录节点 → `dir` → `resources`），
新加的 `_children_of()` 专门认 `dir` 里的子项，`_parse_body` 也改走同一个函数。

**一个必须记住的细节**：第一个文件**没有 `file_index`**（0 被省了），后面从 1 开始。
所以序号只能「有就用、没有按位置补」，不能因为缺键就当成拿不到序号。

**真机响应直接做成了回归用例**（`RealResponseCase`，5 项），并本地跑通了整条链路：

```
请求次数: 1   认出: 6
[0] (无 file_index) 489155.com@FC2PPV-5003668-1.mp4   3522799153
[1] 1              489155.com@FC2PPV-5003668-2.mp4    760233533
[2] 2               台湾uu美少女直播 …mp4              13890047
[3] 3               最 新 位 址 獲 取…txt                    136
[4] 4               社 區 最 新 情 報.mp4               15089802
[5] 5               聚 合 全 網 H 直 播.html                 145
筛选: kept=2  skipped={doc:1, other:1}  by_size=2
sub_file_index: 0,1
```

一次请求、零外网、不碰代理。1.0.28 的钻目录保留着当兜底（别的版本若真把 `dir` 给成路径，
那条路还有用），只是这份真机数据用不上它。

`dist/tgmagnet_1.0.29_x86.fpk`。全量 **423** 项。

## 1.0.28

**「还是一个文件都没认出来」——真因是「目录节点」，不是「没有文件」。**

用户装上 1.0.27 再试同一条磁力，仍然一个文件都认不出。设备面板的「解析磁力」把迅雷
**原话**摆出来了，一眼就能定性：

```json
resources = [{"is_dir": true, "id": "…", "name": "FC2PPV-5003668",
              "file_count": "6", "file_size": 4000000000, "parent_id": "…"}]
```

迅雷对裸磁力只回**一个没展开的根目录节点**，它带着 `file_count = 6`。这个节点被
`_flatten_files` 当成目录丢掉了 —— 于是「认出 0 个文件」，接着去外网抓 `.torrent` 兜底，
而那一刻 NAS 上的代理正好整条不通（`连接超时 38.8s`），兜底也空手而归，最后按全选投递。
三条路一起断，现象就是「还是一个文件都没认出来」。

**改法：清单在下一层，那就往里钻。**

* `_deep_files()`：拍平后如果剩下的全是「没有子节点的目录节点」，逐个展开。
* `_drill()`：一套参数不行换下一套，全在**本机**打（一两百毫秒一次），
  顺序是 `parent_id` → `files/list:parent_id` → `parent_id+list_id` →
  `parent_id+urls` / `urls[]` / `urls+parent_id` → `parent_id+space` → `dir` …
  （迅雷各版本连**接口路径**都不一样：`resource/list` 是「解析这个地址」，
  `files/list` 才是「列这个目录」，两个都试）。
* 参数被无视时（回来还是目录本身）不算成功，接着试下一套——否则会自己递归自己。
* 好使的那套记进 `_CHILD_VARIANT`，同一进程里后续投递直接用它。
* 展开成功后 **不再去外网下 `.torrent`**：那是十几秒起步、代理一抖就全盘皆输的路，
  既然本机已经把真实清单（含 `file_index`，正是 `sub_file_index` 要的序号）拿到了，
  就没理由再跑一趟。`expanded=True` 会一起出现在「解析磁力」的结果里。
* `_is_dir_node()` 认三种目录特征：有子节点 / `is_dir` / **`file_count > 1`**。
  最后那条是为省掉 `is_dir` 的版本准备的；`file_count == 1` 仍是真·单文件种子，
  不当目录钻。

**顺带把「现场试探」做成接口**：`POST /api/xunlei/parse` 现在接受 `{"probe": {…}}`，
把这段请求体原样打给迅雷的解析接口并回原始响应（截断 4 KB）。迅雷字段名千奇百怪，
以后不用为了一次试探就重装一遍 fpk。

**测试**：`tests/test_file_enum.py` 新增 `DrillDownCase` 6 项（目录节点必须钻、
展开后能筛出 2/6、展开后不许再下种子、参数被无视要换下一套、`file_count==1` 不当目录、
`inspect` 带 `expanded`/`expand_sample`），全量 **418**。

`dist/tgmagnet_1.0.28_x86.fpk`。

## 1.0.27

**两件事：「解析不出来任何文件」修掉了；磁力解析搬进搜索框。**

### 一、解析为什么一个文件都认不出来

用户实测反馈「解析不出来任何文件」。设备日志把链条写得很清楚：

```
21:13:00 按 infohash 找到了种子文件：…/download/4754736.torrent
21:13:12 读种子文件失败：经代理 192.168.1.11:7890 连接超时（9.1s）
21:13:36 读种子文件失败：… 连接超时（11.7s）
21:13:56 读种子文件失败：… 连接超时（8.8s）
21:14:53 读种子文件失败：… IncompleteRead(16087 bytes read, 5674 more expected)（7.7s）
```

两个独立的毛病，都得治：

1. **超时给太小**。1.0.26 把 `.torrent` 的超时收到 4～6 秒（当时的判断是「别让人等太久」），
   可走代理连 nyaa **建连本身就要 10 秒上下**（`curl` 实测 10.56 秒拿完一个 21 KB 的种子）。
   收紧到 4 秒 = 每次都失败，日志里那串「连接超时」就是它。现在 15 秒。
2. **断了不会续**。`IncompleteRead(16087 read, 5674 more expected)` —— 代理把响应掐在
   16087 字节，而且**每次断在同一处**，整下重来多少次都一样。那 16 KB 是完好的，
   带 `Range: bytes=16087-` 把剩下的 5674 字节续上就完整了。

新增 `util.http_download()`：带断点续传的下载，按**总预算**（默认 30 秒）而不是按次数控，
因为代理忽快忽慢（同一条 URL 实测 5.8s / 18s / 22s 都有），按次数试的最坏情况会把人干等一分钟。
拿不到就抛错、按「没有清单」降级，**绝不把半截数据当完整的交出去**。

### 二、解析入口搬进搜索框

原来「解析测试」压在设置页「文件筛选」卡片底部，两个毛病：粘一段磁力就把设置标成
「未保存的修改」，而且得先想到去那儿找。

现在并进搜索页：**粘一条磁力，搜索键自己变成「解析磁力」**，点一下或直接回车，
出来的就是「认出 N 个文件 / 来源 / ✓✗ 逐个文件 / 发给迅雷的 `sub_file_index`」，
底下直接带「投递 / 复制」。两个入口（直接搜索、解析后搜）粘磁力时都走这条路——
磁力没有关键词可搜，当普通文本送去检索只会搜出一堆无关结果。

### 三、顺便

- 迅雷接口「再问一轮」：云端解析磁力有时晚一步，第一轮一个都没认出来（或只给个空目录节点）
  时等 1.2 秒重问一遍。本地请求几十毫秒，比跑去外网下种子便宜得多。
- 迅雷**连不上**时不再硬下种子：投递本身马上就会失败，让用户等 30 秒最后拿到「投递失败」没意义。
- 解析面板多给两样东西：响应顶层字段名（`raw_keys`）、以及「找种子地址」这一步的结果
  （找到了 / 站点里没有这条 infohash —— 这跟「地址有了但下不下来」是两种毛病）。

测试：新增 `tests/test_http_download.py`（4 项，含「断在 400 字节→带 Range 续」「服务端
不认 Range→重来而不是拼垃圾」「一直断→抛错并报已拿到多少」）；
`test_ui_markup` 把「解析测试必须在筛选卡片里」改成「必须在搜索页、粘磁力即切按钮」；
`ui_selftest` 49 → 53 项。全量 **412** 通过。

## 1.0.26

**修「文件筛选看着没生效，整包全下了」**。真机实例：任务 `VP6CSuh…`，6 个文件的种子
（2 个正片 mp4、3 个 13～15 MB 的广告 mp4、1 个 txt、1 个 html），规则是「视频 + 字幕、
小于 100 MB 跳过」，本该只留前两个，实际六个全下来了。

链条是：

```

→ 只认出 1 个文件 → total_file_count=1

→ 迅雷按「没指定 = 全选」→ 全下

```

**改法**——清单不再只信迅雷那一句：

| 顺序 | 来源 | 说明 |
| --- | --- | --- |
| 1 | `resource/list` 多套参数 | 先问（本地、毫秒级）；上次好用那套排最前，谁认出 >1 个文件用谁 |
| 2 | `.torrent`（`info.files`） | 它只认出 1 个时才走：顺序就是 BT 的文件顺序 = `sub_file_index` 序号；搜索结果自带地址，裸磁力按 infohash 现找 |
| 3 | 都没有 | 不发 `sub_file_index`，**回执明写「这次是整个种子全下」** |

顺序是有讲究的：下种子要出网、走代理还可能超时（实测被掐断过），而本地接口是毫秒级；

以前直接抛出去，现在归到可重试的网络错误里。

迅雷每次尝试的原始响应结构。只问不投，是给「筛选到底有没有生效」这类问题准备的望远镜。

顺手把回执改成诚实版：以前没拿到清单时报「1 个文件」，现在报「没拿到文件清单（迅雷只回了

## 1.0.23

**症状**：在飞牛 App 里打开面板，原生标题栏「磁力管家 · 概览」下面还有一整条空白
（约 96px），第一排数据卡片被顶到半屏以下；抽屉菜单同样被顶下去一大截。

**原因**：飞牛 App 用的是内嵌 webview。这个 webview 的 `safe-area-inset-top`
报的是「状态栏 + 原生标题栏」的**整段**高度（实测 ≈96px），而网页本身早就排在

`@media (display-mode:standalone)`（加到桌面、独立运行时才真的会盖住状态栏）才取
`env(safe-area-inset-top)`。`.topbar` 和抽屉的 `padding-top` 都改成吃 `--sat`。

|---|---|---|
| 手机顶栏高度 | 152px（含 96px 死白） | **56px** |
| 首屏第一排卡片位置 | 被压到 162px 起 | 66px 起 |
| 抽屉顶部留白 | 18 + 96px | 18px |

底部没这个毛病：同一个 webview 里 `safe-area-inset-bottom` 实测就是 0，
底部标签栏照旧用 `env(safe-area-inset-bottom)`，独立运行时仍然躲开 Home 条。

测试：`tests/test_ui_markup.py` 新增 1 条（顶栏/抽屉不许直接用 `env(顶部安全区)`，

这轮的问题是「关闭自动投递，信息流转到哪里？迅雷上有操作什么吗？检查一下功能虚实」。查下来有一处是真的不符：

- 面板文案补边界：概览「自动投递」副标题改成「收到就下；关掉只回结果」，下载页开关下方加一段说明。

## 1.0.18

- 回答「手机上在飞牛 App 里操作也能连上迅雷，还是必须回电脑浏览器」：**都能，不用回电脑**。连迅雷的是 NAS 里的后台进程去请求本机 `127.0.0.1:5666 / :2345`，App、浏览器、手机只是发指令的遥控器。唯一差别是 `fnos-token` 取自「打开面板那个客户端的 Cookie」——从飞牛桌面或 App 入口进会带，直接输 `IP:8470` 不带；已存进配置的令牌照常可用，只影响「再抓一次新令牌」这一步。
- 修日志里反复出现的 `轮询异常: getUpdates 请求失败: HTTP 409`：409 的唯一含义是「同一串 Bot Token 还有另一个地方在 `getUpdates`」，原来只当普通异常、退避到 60 秒再撞一次，日志一直刷且看不出该停谁。现在分三种处理：
  - 第一次撞：判成「自己人打架」（面板点重连、旧的长轮询还没退），等 3 秒静默重试，不告警；
  - 连撞两次：先查 `getWebhookInfo`，有 webhook 就自动清掉改回长轮询（`telegram.auto_clear_webhook`，默认开）；
  - 确实没有 webhook：说明另一处实例在抢，退避 5 分钟、**只告警一次**，并写明三个排查方向（另一台设备、旧进程没退干净、设过 webhook）。
- 报错不再只是裸 409：`TelegramError` 纳入 `error_code`，HTTP 非 2xx 会把 Telegram 响应体里的 `description` 一起打出来（`（服务端原话：Conflict: terminated by other…）`）。
- 轮询线程加代际：`stop()` 让还在长轮询里挂着的那条线程回来后直接退出，不再和新连接互抢一轮；被顶掉的那条也不再刷 WARNING。
- 面板：`/api/status` 增 `bot.poll_state` / `bot.poll_hint`，冲突时侧栏显示「轮询冲突」+ 红字提示，恢复后自动消失。

## 1.0.17

- 回答「迅雷令牌还有 2 天后到期，会自动续期吗」：**不会自己续**。`pan_auth` 是迅雷账号的会话令牌，续期握在迅雷手里——要么迅雷套件自己续，要么重新登录迅雷账号；程序没有账号密码，也没有可调的刷新接口。
- 能做的是「接住」迅雷续好的那个：剩不到 48 小时（`token_watch_hours`）开始，每 6 小时（`token_retry_hours`）从本机重扫一次令牌，只有过期时间更晚才写进配置，避免把刚续好的换回旧的。
- 投递前也先看一眼：快到期就先换新再投，不用等第一条消息因为 `invalid token` 失败才发现；换到了会在回复里注明「已换用本机找到的令牌」。
- 换不到就提前提醒：剩不到 72 小时（`token_warn_hours`）面板顶栏挂一个可点的胶囊「迅雷令牌 还有 2 天后到期」，点它立刻重抓；日志 WARNING 与事件各记一条，同一条令牌只提醒一次，不刷屏。
- 新增 `GET /api/status` 的 `xunlei_token` 字段与 `POST /api/xunlei/refresh-token` 接口；心跳每半小时检查一次（内部节流）。
