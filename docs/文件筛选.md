# 多文件种子：只下其中几个文件

> 结论先说：**迅雷接口支持自定义文件选择**，字段是 `sub_file_index`。
> 1.0.20 及以前的实现只用了「全选 / 按扩展名硬筛」两档，1.0.21 把中间档补齐：
> 类别、大小、名称三条规则，面板可配，回执会说清跳过了什么。
>
> 本版**没做**「粘磁力看文件列表、手工勾选」那个界面，原因见第四节末尾。

---

## 零、这条规则管到哪儿（1.0.25）

**管所有投递**。配置只有一份（`download.xunlei.file_filter`），读取只有一处
（`XunleiDownloader.add` → `_post_task` → `select_files`），所以只要能走到迅雷的入口，
就一定会被同一套规则筛一遍：

| 入口 | 谁触发 | 代码路径 |
| --- | --- | --- |
| 搜索后自动投递 | 收到一段文字，检索命中第一条 | `handle_text` → `submit` |
| 磁力直达 | 消息里自带 `magnet:` | `handle_magnets` → `submit` |
| 关掉自动投递后补投 | 回执上那个「⬇️ 现在下」按钮 | `submit` |
| 面板「投递」 | 搜索结果卡片 / 磁力列表 | `webui._download` → `submit` |

`tests/test_filter_scope.py` 把这四条各跑一遍，断言它们发出去的 `sub_file_index` 完全一样
（同一个合集包 → `0,1`），所以「某条路偷偷绕过筛选」这种改动会立刻红。

三个边界也说清楚，免得以为是 bug：

1. **总开关就是「文件筛选」那个开关**（存的是 `select_all_files`，反义）。1.0.25 起它默认
   **开**，也就是默认按规则挑；关掉才是「多文件种子一律全下」。以前它叫「多文件种子全选」，
   挂在筛选区外面，很容易让人以为筛选只管某一条路径——现在它长在筛选区里面。
2. **单文件种子也过规则**。只有一个文件的磁力（很常见的「直链」形态）会被类别/大小/名称
   判一遍：留下的照常投（不传序号，只有一个文件不用指），被判掉时按 `fallback_all` 兜底，
   兜底关掉就**不投**并在回执里说「全筛掉了」。1.0.24 及以前这里是直接跳过筛选的。
3. **换后端就管不着了**。规则配在迅雷下面，`download.fallback` 里 aria2 / qBittorrent 接手的
   那次不做文件选择（它们要另外解析种子才能指定文件，本版没做）。所以那种情况回执会明写
   「这次是 aria2 下的，文件筛选只对迅雷生效，种子里有什么就下什么」，不会装作筛过了。

## 零点五、清单到底从哪来（1.0.26，真机踩坑后重写）

1.0.25 上线当天就被抓到一个「规则明明开着，整包全下了」。查下来链条很干脆：

```
/drive/v1/resource/list 对这条磁力只回了一个节点（一个没展开的目录）
→ _flatten_files 只认出 1 个「文件」→ total_file_count = 1
→ total <= 1 时不发 sub_file_index（迅雷的规矩：单文件不用指）
→ 迅雷按「没指定就全选」处理 → 6 个文件全下
→ 回执还写着「已投递迅雷（1 个文件）」，看着像正常
```

那个种子是：2 个正片 mp4（3.3 GB / 725 MB）、3 个广告 mp4（13～15 MB）、1 个 txt、1 个 html。
规则「视频 + 字幕、小于 100 MB 跳过」本该只留前两个，实际一个没筛。

现在清单分三条路取，不再只信迅雷那一句：

| 顺序 | 来源 | 说明 |
| --- | --- | --- |
| 0 | **往目录节点里钻**（1.0.28） | 迅雷对裸磁力常常只回一个 `is_dir` 的根目录节点（带 `file_count`）。它既不是「一个文件」也不是「没有文件」，而是「清单在下一层」——按 `parent_id` / `list_id` / `files/list` 等多套参数在本机把它展开，拿到真实文件（含 `file_index`，正是 `sub_file_index` 的序号）。全在本机跑，一次一两百毫秒 |
| 1 | `resource/list` 的几套参数 | **先问迅雷**（本地、几十毫秒）：上次好用那套排最前，逐套试，谁认出多于一个文件就用谁。它返回节点自带的 `file_index` 正是 `sub_file_index` 要的序号 |
| 2 | `.torrent` 的 `info.files` | 连目录都钻不动时才走这条：`info.files` 的顺序就是 BT 的文件顺序，也就是 `sub_file_index` 的序号。搜索结果自带地址；裸磁力按 infohash 现找 |
| 3 | 都没有 | **不发 `sub_file_index`，并在回执里明说「这次是整个种子全下」** |

顺序不能反：走代理下种子偶尔要十几秒甚至超时，本地接口却没这毛病；只要迅雷给了完整树，
就没理由再跑一趟外网。第 0 条是 1.0.28 补上的——它才是「迅雷只回一个目录节点」的正解，
第 2 条只是兜底（真机上代理不通时，兜底那次 40 秒都没拿到东西）。
顺带解决了「序号语义（含不含目录、0 还是 1 起）」这个一直没验证的问题——展开来的
`file_index` 和种子里的文件顺序都是确定的，没有目录占号。

第 3 条是诚实性要求：**宁可说「没认出来、这次全下」，也不能报「1 个文件」让人以为筛过了。**

第 2 条这条路本身也踩过两个坑，都写进代码注释了：① 代理会在半路把响应掐断
（`IncompleteRead: 16087 read, 5674 more expected`，每次断在同一处），整下重来多少次
都一样，只有带 `Range` 从断点续才拼得出完整文件（`util.http_download`）；② 建连本身就要
10 秒上下，超时给 4～6 秒等于必然失败。

配套的排查入口在**搜索页**：把一条磁力粘进搜索框，右边的键自己会变成「解析磁力」，点下去
（或直接回车）就会列出：认出几个文件、从哪个来源认出来的、按当前规则会挑哪几个（✓/✗）、
发出去的 `sub_file_index` 是什么；认不出来时还能展开看每次尝试的结果。只问不投，不会建任务。

放搜索页而不是设置页，是因为它是**读**的操作，不是配置：原来压在「文件筛选」卡片里，
粘一段磁力就把设置标成「未保存」，还得先想到去那儿找。

## 一、迅雷接口能做到什么

创建任务的接口是 `POST /drive/v1/task`，`params` 里有两个字段配合决定下载哪些文件：

| 字段 | 取值 | 含义 |
| --- | --- | --- |
| `total_file_count` | 文件总数 | 种子里一共有几个文件 |
| `sub_file_index` | `-1` | 全选 |
| | `0,2,5` | 只下这几个（**全局序号，逗号分隔，0 起**） |
| | 不传 | 单文件种子时不传（`total_file_count == 1`） |

文件列表从 `POST /drive/v1/resource/list` 拿，返回 `resources` 文件树（目录 + 文件，带
`name` / `file_size` / `mime_type`），程序按 DFS 先序拍平成一条平铺列表，序号即 `sub_file_index` 用的序号。

### 支持，但有三个约束

1. **`sub_file_index` 是可选字段，各版本认法不一**。磁力能解析（说明令牌有效）却仍被拒时，
   程序会自动发一次精简请求，把 `mime_type` 和 `sub_file_index` 一起砍掉——
   **这一刀下去，筛选就变成全选了**。所以「筛选生效了没有」必须在回执里写清楚。
2. **序号语义依赖 `resources` 的返回顺序**。文档只写了「全局索引」，没写目录算不算一个号。
   程序优先用节点自带的 `file_index`，没有才退回拍平位置。这两者在「目录也占号」的版本上会错位。
3. **空选择必须兜底**。一个文件都没留下时，现在的代码会拼出 `sub_file_index = ""`（空字符串），
   迅雷收到等于「一个都不要」——要么建出一个空任务，要么直接 400。

三条里第 1、3 条是程序能自己处理的，第 2 条只能靠「预览」让人眼确认一次。

## 二、现状盘点

已经有的：

- `download.xunlei.select_all_files`（1.0.25 起默认 `false` = 按规则挑）：筛选总开关，面板下载页有开关；
- `_flatten_files()`：文件树拍平，保持 DFS 先序；
- `_select_indices()`：全选时返回 `None`（发 `-1`），否则按扩展名白名单挑。

缺的和错的（1.0.21 已全部处理）：

| 问题 | 现象 | 处理 |
| --- | --- | --- |
| 空选择发空串 | 种子全是 exe/7z 时 `sub_file_index = ""`，迅雷收到等于「一个都不要」 | 兜底成全选并在回执里说明；也可配成宁可不投 |
| `filter_files` 是个幽灵键 | `_select_indices` 读 `self.cfg.get("filter_files", True)`，但 `xunlei` 段里没有这个键、面板也没有、文档也没提——所以扩展名白名单**永远是开的**，用户既关不掉也调不了 | 用 `file_filter` 明确取代它 |
| 没有大小门槛 | 一个 40 GB 的合集包，只要含 mkv 就整包下 | 加 `min_size_mb` / `max_size_mb`，字幕豁免 |
| 图片默认会被下 | `.jpg` 在 `INFO_EXT` 里，所以关掉全选后封面图照样下 | 图片独立成类别，默认不选 |
| 选了几个不说 | 回执只说「已投递迅雷（38 个文件）」，看不出筛选有没有生效 | 回执写「挑了 12 / 38」并列出跳过的分类 |
| 精简重试静默丢筛选 | 鉴权兜底会砍掉 `sub_file_index`，于是全下，但没人说 | 回执明写「本次筛选没生效」 |

## 三、筛选规则设计

### 3.1 按类别

一个文件先按扩展名归到唯一类别，再看这个类别要不要：

| 类别 | 扩展名 | 默认 |
| --- | --- | --- |
| 视频 | mkv mp4 avi rmvb rm wmv flv mov ts m4v webm vob mpg mpeg 3gp f4v ogv iso | 要 |
| 字幕 | srt ass ssa sub idx sup | 要 |
| 图片 | jpg jpeg png gif webp bmp | 不要 |
| 说明 | nfo txt md diz sfv | 不要 |
| 压缩包 | zip rar 7z tar gz | 不要 |
| 其他 | 其余 | 不要 |

默认只下「视频 + 字幕」——绝大多数场景就是这样，也是把「关掉全选」变得有用的关键
（现在的实现会把封面图一起下）。

### 3.2 按大小

- `min_size_mb`：小于这个值的**视频/压缩包/其他**不要。默认 `0`（不限）。
  常填 `100`——专门挡「几 MB 的预告片、样片、广告」这种合集包里常见的小垃圾。
- `max_size_mb`：大于这个值不要。默认 `0`（不限）。用来挡「一个 80 GB 的原盘」。
- **字幕和说明豁免大小限制**：字幕天生就几十 KB，按 100 MB 筛等于把字幕全删了。
  这个豁免默认开着（`subtitle_exempt_size`），要严格筛可以关掉。

### 3.3 按名称

- `name_exclude`：命中就丢，逗号分隔，比如 `sample,trailer,预览,广告`。
- `name_include`：填了就只留命中的（AND 的关系，逗号分隔要全含）。留空表示不按名称挑。

### 3.4 判定顺序（顺序会影响结果，必须写死）

```
1. 单文件种子            → 不传 sub_file_index，直接完事
2. 全选开关开着          → -1
3. 类别不在白名单        → 丢
4. 命中 name_exclude     → 丢
5. name_include 非空且未全含 → 丢
6. 大小超范围（字幕豁免）  → 丢
7. 剩下为空              → 兜底成全选，并在回执里说明「规则把文件全筛掉了，已改回全选」
```

第 7 步是强制的：宁可多下，也不能投一个空任务出去——那个任务在迅雷里会是个没有文件的空壳，
用户还得自己去删。

### 3.5 回执要说什么

投递成功后，回复里除了「已投递」还要有筛选结果：

```
✅ 已投递 xunlei · #1234567890
　 38 个文件里挑了 12 个（4.7 GB / 12.1 GB）
　 跳过：图片 18 · 说明 6 · 小于 100 MB 2
```

这样「筛选到底生效没有」一眼可见，不用去迅雷里数文件。

## 四、面板交互（1.0.21 已实现）

### 4.1 下载页「文件筛选」这张卡里（1.0.25 起总开关就在卡里）

```
文件筛选              [开关]  ← 默认开：按规则挑
  对自动投递、点「下载」补投、直接发磁力链接都生效；关掉 = 多文件种子一律全下
筛选条件  生效中：所有投递都按下面规则挑
类别      [视频✓] [字幕✓] [图片] [说明] [压缩包] [其他]
大小      最小 [ 100 ] MB   最大 [ 0 ] MB     0 = 不限
名称      包含 [          ]    排除 [sample,trailer,预览]
          [☑] 字幕和说明不受大小限制
说明      只下勾选的 2 类；小于 100 MB 的跳过（字幕和说明除外）；一个都没留下时会自动改回全选。
```

- 关掉总开关时整块条件**变淡**，状态写「已关闭：多文件种子一律全下」，说明里补一句
  「也包括手动补投和磁力直链——它们走的是同一份规则」。不置灰是有意的：先配好规则、再开关，
  比「关掉才允许配」顺手；
- 底部那句说明是实时算的，勾了几个类别、门槛多少，改一下就变，不用保存也能看到后果。

### 4.2 为什么没做「粘磁力手工勾选」

原计划里有个预览界面：粘一个磁力，列出文件表，手工打勾后按勾选投递。这一版没做，原因是
**它要解决的问题（规则够不够用）现在还不知道**，而它带来的成本是确定的：

- 要新增两个接口和一个弹窗，只能一次性用完，不能复用；
- 手机上手点几十个复选框本来就不舒服，合集动辄 30+ 个文件、还要翻页；
- 真正高频的场景是「这个作者/这类合集，我永远只要正片和字幕」——那正是规则能表达的。

所以先让规则跑一段，看回执里的「跳过：图片 18 · 说明 6 · 小于 100 MB 2」够不够解释结果。
如果经常出现「这次只想下第 3、7 集」这种规则表达不了的需求，再补预览界面也不迟——
底层的 `sub_file_index` 传法已经通了，加界面不涉及改协议。

### 4.3 序号语义仍需真机确认

程序优先用 `resources` 节点自带的 `file_index`，没有才退回「拍平后的位置」。
「全局索引」到底含不含目录、从 0 还是从 1 起，官方没写，只能实测。
**验证办法**：拿一个文件结构已知的小种子（比如 3 集的剧，每集大小不同），
把「最小 MB」设成一个只留下一集的阈值，投递后去迅雷看下的是不是那一集。
在验证之前，本功能的价值是「大概率对」，不是「保证对」——所以每次都会把
「挑了 12 / 38」写进回执，错了一眼能看出来。

## 五、配置结构

```json
"download": {
  "xunlei": {
    "select_all_files": false,
    "file_filter": {
      "video": true,
      "subtitle": true,
      "image": false,
      "doc": false,
      "archive": false,
      "other": false,
      "min_size_mb": 100,
      "max_size_mb": 0,
      "name_include": "",
      "name_exclude": "",
      "subtitle_exempt_size": true,
      "fallback_all": true
    }
  }
}
```

`select_all_files` 是**反义字段**（`true` = 全选 = 不筛），1.0.25 起默认 `false`。
没写这个键的老配置按 `false` 处理——筛选是全局规则，不该因为缺字段就悄悄失效。

`filter_files` 这个幽灵键被 `file_filter` 取代。老配置里如果手动写过 `filter_files`，
按「没写 `file_filter`」处理，行为退回默认（视频+字幕）。

## 六、风险与验证顺序

已经用测试锁住的（`tests/test_file_filter.py` 31 项 + `tests/test_filter_scope.py` 11 项）：

- 类别判定与六个开关的组合；
- 大小门槛、字幕豁免、拿不到大小不误删；
- 名称包含/排除，以及「排除优先于包含」；
- 空结果兜底成全选、关掉兜底则一个请求都不发；
- 单文件种子不传 `sub_file_index`（但它照样过规则，被判掉时按兜底走）；
- 精简重试把筛选砍掉时，回执里有「本次筛选没生效」；
- 筛选说明一路传到 Telegram 回执；
- **四条投递入口发出的序号完全一致**，全选是唯一的总闸，换 aria2/qb 时回执承认管不着。

只能上真机验的（还没做）：

1. **序号语义**：拿一个 3 集的剧、每集大小不同，把「最小 MB」设成只留下一集的阈值，
   投递后去迅雷看下的是不是那一集。在这之前本功能是「大概率对」而非「保证对」。
2. **真实 `resources` 里有没有 `file_index`**：没有的话走的是拍平位置，
   目录占不占号就成了关键。看日志里 `多文件种子按规则挑了 12/38：0,1,2...` 这行，
   再和迅雷里实际出现的文件对照。
3. **精简重试的触发条件**：目前只在「磁力能解析但建任务被拒」时才会走到，
   平时不会。真要验，把下载目录 id 填成一个不存在的值即可。
