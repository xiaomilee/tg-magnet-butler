# 开关与信息流：一条消息到底走到哪

这篇回答三个问题：消息进来之后**每一步做什么**、**每个开关管到哪一步**、
**关掉之后哪些事仍然发生**。写它的起因是有人问「关闭自动投递，信息流转到哪里？迅雷上有操作什么吗」——
当时的答案和界面上写的并不完全一致（自带磁力的消息会绕过开关），所以这里按代码实际行为逐条对齐。

---

## 1. 一条消息的完整路径

```
Telegram 消息
   │  ← 机器人暂停（/pause 或面板「暂停」）在这一步就拦掉：不检索、不投递，只回一句提示
   ▼
① 解析 intake.py          判定走哪条路：自带磁力 / FC2 编号 / 整段检索（不联网）
   ▼
② 历史字典 library.py     这次要搜的东西，库里是不是已经有了（要 library.roots 非空且开关开）
   │                       命中且允许拦 → 到此为止，不检索、不投递，回复里告诉你「已经在库里」
   ▼
③ 检索 nyaa.py            sukebei 拉列表（走代理线路表：telegram.proxy 起、proxy_channels 往后，谁通用谁）
   ▼
④ 分析 analyzer.py        过滤（做种/体积/排除词） → 打分排序 → 挑出前 N 条
   ▼
⑤ 自动投递 pipeline.py    全局开关 + 规则开关都为真，才挑第 pick 名往下走
   │                       关掉任一个 → 停在这里，只回结果列表 + ⬇️ 按钮
   ▼
⑥ 去重 store.py           infohash 在 app.dedupe_days 天内投过 → 跳过
   ▼
⑦ 投递 downloaders/       迅雷（或 aria2 / qBittorrent 兜底），成功后写 downloads 表
   ▼
⑧ 回复 bot.py             结果列表 / 投递结果 + ⬇️ 按钮（按钮回调再走一次 ⑥⑦）
```

每一步留下来的痕迹：

| 步骤 | 写到哪 | 面板哪里能看到 |
| --- | --- | --- |
| ①② 判定与字典 | `events` 表（`library_hit` 等） | 运行日志 |
| ③④ 检索结果 | `searches` 表（含前 10 条候选，供 ⬇️ 按钮取用；90 天后清理） | **看不到**，只在 Telegram 消息的按钮里 |
| ⑥⑦ 投递 | `downloads` 表 | 概览「最近投递」、`/stats`、`/api/history` |
| 全部 | `events` 表 | 运行日志 |

> 也就是说：**关掉自动投递后，「最近投递」是空的**，但检索本身照做、结果仍然落在 `searches` 里，
> Telegram 那条消息上的 ⬇️ 按钮一直可用（按钮按 `rid` 回查这条记录）。

## 2. 开关对照表（以代码为准）

| 开关 | 配置键 | 管哪一步 | 关掉之后 |
| --- | --- | --- | --- |
| 自动投递 | `download.auto_download` | ⑤ | 检索照做、结果照回、按钮照给，**不往迅雷加任务**（自带磁力的消息也一样，见 §3） |
| 规则自带的自动投递 | `rules[].auto_download` | ⑤ | 只对命中这条规则的消息生效；回复里会写明是哪条规则关的 |
| 自动投递第几名 | `download.auto_pick` / `rules[].pick` | ⑤ | — |
| 检索前查字典 | `library.check_search` | ② | 完全不查，直接检索 |
| 跳过已下载 | `library.skip_download` | ② | 库里已有也放行（回复里仍会提醒「库里已有」） |
| 跳过「曾删过」 | `library.skip_deleted` | ② | 以前有、现在删了的也放行 |
| 机器人暂停 | 内存态（`bot.paused`） | 消息入口 | 非命令消息一律不处理（含自带磁力的）；命令仍可用；重启后恢复成「不暂停」 |
| 去重窗口 | `app.dedupe_days` | ⑥ | 同一 infohash 在窗口内只投一次，**手动点按钮也算** |

三个容易被误会的点：

1. **`/pause` 停的是「接收」，不是「自动投递」。** 暂停期间连检索都不做，`/search` 这类命令不受影响。
2. **规则开关是「与」的关系**：全局开、规则关 → 这条规则的消息不自动投；全局关则无论如何都不投。
3. **手动点 ⬇️ 不看自动投递开关**（那是你明确要下这一条），但**照旧看去重**。

---

## 3. 关闭自动投递之后，迅雷上有什么变化

**没有。**

投递是唯一会碰迅雷的动作，它集中在 `pipeline.submit()`：
发一次 `POST /drive/v1/task`（`type: user#download-url`），迅雷收到后**立刻开始下载**，
落到配置里的下载目录（没配就落迅雷默认目录）。关掉自动投递，这个请求根本不会发出。

按消息形态分：

| 消息形态 | 关掉自动投递后 | 迅雷上 |
| --- | --- | --- |
| 普通文字（含 FC2 编号） | 检索 → 结果列表 → 等你点 ⬇️ | 无变化 |
| 自带磁力 | 不检索，只回「这条磁力 + ⬇️ 1」并注明「还没进迅雷」 | 无变化 |

> 1.0.19 及以前，**自带磁力的消息不受这个开关约束**，照样直接投。已修：
> `handle_magnets()` 现在接收 `want` 参数，关掉即只收不发，并挂出按钮。
> 命令行 `main.py --parse ... --send` 属于「人明确要求现在投」，仍然直接投。

## 4. 「已经关了还在下」的排查顺序

1. 面板概览 → 快捷开关：自动投递是不是真的关着（`/api/status` 的 `download.auto`）；
2. 命中规则自己开了自动投递？回复里会写「规则 X 关掉了自动投递」，没写就不是规则问题；
3. 是不是点了历史消息里的 ⬇️ 按钮——按钮绕开开关；
4. 是不是别的设备/容器跑着同一份配置（同一个 Bot Token 会 409，见 README 9.8）。

---

## 5. 设计目标（按优先级）

1. **不替人做不可逆的事。** 往迅雷加任务会占带宽、占空间，所以「下不下」的最后一步必须能被一个开关彻底关掉，
   关掉之后的效果要能从回复里一眼看出来，而不是让人去翻日志。
2. **关掉不等于丢东西。** 检索结果仍然落库、按钮仍然可用，随时能补投；不作废、不静默。
3. **每条提示都要指认到具体开关。** 「没下载」要说明是全局关的、还是哪条规则关的，不写「配置问题」这种话。
4. **手动操作不受自动开关约束，但受去重约束。** 人点按钮就是明确意图，但同一 infohash 不该在窗口内下两遍。
