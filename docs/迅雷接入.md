# 迅雷接入说明

## 0. 不用配，它自己会连

程序**启动时**就会自动侦测（网关端口 / 应用目录 / 令牌），打通就把配置写好并复测。
面板**概览页**一眼能看到结果：「下载后端」那张卡写着「迅雷」和连接状态（`已连接 · 网关 :5666`），
快捷开关里还有一格「迅雷 / 立即重连」——断了就在那儿点一下，不用翻页
（1.0.32 起「下载与迅雷」整页收进存档，导航里没有入口了）。
也可以命令行手动来一次：

```bash
python3 /var/apps/tgmagnet/target/main.py --detect          # 只看结果
python3 /var/apps/tgmagnet/target/main.py --detect --apply  # 打通就写配置并复测
```

它做的事：

| 步骤 | 依据 |
| --- | --- |
| 找安装 | 扫 `/var/apps/*`、`/vol*/@appstore/*` 等目录名带 `xunlei` / `迅雷` 的路径 |
| 找进程 | 读 `/proc/*/cmdline`，命令行里带 xunlei 的进程，并从参数里抠端口 |
| 找端口 | 解析 `/proc/net/tcp{,6}` 的 LISTEN 状态，取 2340–2360 段与配置里的端口 |
| 指纹识别 | 逐个端口打 `GET /cgi/ThirdParty/xunlei/index.cgi/drive/v1/tasks?type=user%23runner`，按 200 / 401 / 404 判断这端口上有没有迅雷、缺哪个令牌（HTML 只说明「这端口跑了别的网页」，不算命中） |
| 找令牌 | 先在**套件首页**里找（新版把 `pan_auth` 内联在 `uiauth()` 里，1.0.42）；找不到才退回扫目录，读 ≤512 KB 的文本类文件 |
| 复用登录态 | 从飞牛桌面打开本面板时，浏览器带来的整条 Cookie（`fnwg_token` + `ost`）会直接写进配置（不再只留在内存里） |

**能自动到什么程度**：位置、模式、端口、以及「缺哪个令牌」都能自动；`pan_auth` 是迅雷账号的登录态，服务端不会凭空给出，捞不到时仍然要手抄一次（下面第 1、2 节）。网关模式通常不需要手抄 —— 飞牛登录态已经在你浏览器里了。

**安全说明**：明文令牌只用于写入 `{etc}/config.json`（0600），面板返回的总是掩码（`abcd…1234`）；探测没打通时**不会**覆盖你现有的配置，只把建议值打出来。

---

本应用不依赖迅雷客户端，只调用迅雷自己的 HTTP 接口。接口形态来自实际项目
（[chhc007/Fnos-Qbit2xunlei](https://github.com/chhc007/Fnos-Qbit2xunlei)、
[pyxunlei](https://github.com/huihuidehui/pyxunlei)）验证过的调用方式：

| 用途 | 方法与路径 | 关键参数 |
| --- | --- | --- |
| 解析设备空间 | `GET /drive/v1/tasks?type=user%23runner&limit=20` | 返回里取 `params.target`（形如 `device#xxxx`） |
| 解析磁力/种子 | `POST /drive/v1/resource/list` | body `{"urls": magnet, "page_size": 2000}` |
| 创建下载任务 | `POST /drive/v1/task` | body 见下 |
| 查询任务 | `GET /drive/v1/tasks` | — |

创建任务的 body（程序会自动组装，这里只是让你知道字段含义）：

```json
{
  "type": "user#download-url",
  "name": "任务名",
  "file_name": "文件名",
  "file_size": "123456",
  "space": "device#hash",
  "params": {
    "url": "magnet:?xt=urn:btih:...",
    "target": "device#hash",
    "total_file_count": "3",
    "mime_type": "video/x-matroska",
    "sub_file_index": "-1",
    "parent_folder_id": "…",
    "parent_folder_path": "…"
  }
}
```

- `sub_file_index = "-1"` 表示全选；也可以是 `0,2,5` 这样的全局索引；
- `total_file_count = 1` 时不传 `sub_file_index`；
- **空字符串不是「什么都不下」，而是个雷**：规则把文件全筛掉时如果发 `""`，
  迅雷那边会建出一个没有文件的空壳任务（或者直接 400）。本程序在这种情况下改发 `-1`，
  并在回执里说明「规则把文件全筛掉了，已改回全选」。挑选规则见 [文件筛选.md](文件筛选.md)；
- `parent_folder_id` 是**目录 id，不是路径**，且只在当前设备空间里有效（换设备、重装迅雷、删掉目录都会失效，
  失效时迅雷回 `parent folder not found`）。**留空就落到迅雷默认下载目录**，这也是最省事的用法；
  要固定目录，用 `parent_folder_id` + `parent_folder_path` 成对传，且目录必须真实存在；
- `space` 与 `params.target` 必须是同一个值，且**不要硬编码**，每次从 runner 任务里取。

## 唯一的接法：飞牛网关（官方迅雷套件）

1.0.31 起删掉了「2345 面板」那条接法。原因很具体：`mode` 的默认值一直是 `panel`，
而这台机器上只装了应用中心的官方套件——2345 没人监听，程序每次都在拿
`连接被拒绝（errno 111）`，报出来却是「未取到设备空间」，很难看出是端口的事。

现在只走飞牛网关 `/cgi/ThirdParty/xunlei/index.cgi`，需要两串东西：

| 配置 | 从哪来 |
| --- | --- |
| `pan_auth` | 迅雷自己的登录态；新版套件把它内联在首页的 `uiauth()` 里，程序会自己读（1.0.42），读不到才手抄（浏览器打开迅雷下载页，F12 → Network → 任意 `/drive/v1/...` 请求的 query 里） |
| `fnos_cookie` | 飞牛的登录 Cookie；新版飞牛要的是里面的 `fnwg_token` + `ost`。**从飞牛桌面打开一次本面板**，浏览器会带过来并自动写进配置 |

端口（`fnos_port`，默认 5666）也由自动侦测决定：飞牛 Web 端口改过的话，它会从
`/proc/net/tcp` 里找实际在监听的 56xx 端口试一遍，不用你填。

## 模式二：`fnos_gateway`

适用于：飞牛应用中心里的官方「迅雷」App —— 它的接口挂在飞牛网关下：

```
http://<nas>:<飞牛端口>/cgi/ThirdParty/xunlei/index.cgi/drive/v1/task?pan_auth=...&device_space=
```

配置：

```
mode        = fnos_gateway
host        = 127.0.0.1
fnos_port   = 5666          # 飞牛 Web 端口
pan_auth    = <令牌>
fnos_cookie = <整条 Cookie>
```

### 关于 `pan_auth` 的形状（1.0.41）

它必须是 **JWT 本身**：形如 `eyJhbGciOi…（三段，用 `.` 分隔），通常 200~600 字符。

从 F12 里复制时很容易把它连地址一起抄下来，变成：

```
http://192.168.1.2:5666/cgi/ThirdParty/xunlei/index.cgi/device/info/watch?pan_auth=eyJ…&device_space=
```

存成这样，网关会把整条地址当 token 发给迅雷云，回来的是

```
checkAuth failed: token contains an invalid number of segments
```

**这句话说的是「段数不对」，不是「过期」**——以前看到它去重登、去重抓，全是白忙。
1.0.41 起不用管：读配置、存配置、发请求三处都会自动把里面那段 JWT 掐出来，
设置页也写明了。真遇到面板提示「不是 JWT」，把 `pan_auth=` 后面那一段单独粘进去即可。

### 取飞牛登录 Cookie（1.0.42）

**新版飞牛（迅雷套件 3.23.5 起）改了这一层的规矩**，这是 2026-11-14 拿真 Cookie
逐项剥离实测出来的：

| Cookie 组合 | 结果 |
| --- | --- |
| `fnwg_token` + `ost` | ✅ 200，任务列表正常 |
| 上面再加一个 `fnos-token` | ❌ `invalid token`（放最前、放最后都一样） |
| 只有 `fnwg_token` | ❌ `invalid token` |
| 只有老 `fnos-token` | ❌ `invalid token` |

也就是说：**要 `fnwg_token` + `ost` 这一对，而 `fnos-token` 一旦出现就被整条拒**。
`osrt` / `xtoken` 可带可不带（`xtoken` 只有 60 秒寿命，别指望它）。
网关拒人时回的是 13 字节纯文本 `invalid token`，状态码还是 200——很容易被读成
「迅雷云说令牌过期」，其实连静态页都进不去。

**首选：什么也别抄。** 从飞牛桌面点开本面板，浏览器会把整条 Cookie 一起带过来，
程序读到就**直接写进配置**（网关模式下才写），Telegram、定时任务、失败重试因此都能用上。
面板「令牌来源」那一行会写清：是浏览器带来的、手动填的，还是自动侦测写的，以及多久之前。

**保底：整条粘一次。** 浏览器打开飞牛 / 迅雷套件 → F12 → Network → 点一条
`drive/v1` 请求 → 复制请求头里 `Cookie:` 整行 → 粘到设置页「飞牛登录 Cookie」。

不用自己挑项：`util.clean_fnos_cookie()` 会做三件事——去掉 `Cookie:` 前缀和引号、
处理多行粘贴、**在有 `fnwg_token` 时把 `fnos-token` 整项剔掉**（留着就是把自己锁在门外）。

**顺带白捡 `pan_auth`。** 只要 Cookie 是好的，程序会 `GET <网关>/` 打开套件首页，
用正则把内联的 `uiauth(value){ return "eyJ…" }` 读出来——首页打得开就说明 Cookie 有效，
于是「读得通、写不通」这类判断也不用再猜。这也是 1.0.42 起令牌轮换能自动跟上的原因。

> 老的 `fnos_token` 字段还在（老版飞牛仍用它），但两个都在时以 `fnos_cookie` 为准，
> 而且绝不会再把 `fnos-token=` 拼进 Cookie 里。

## 失败降级

投递顺序：`backend` → `fallback[]`，任何一步成功就停。全部失败时：

- Telegram 里回一条 ⚠️ 失败原因 + 原始磁力链接（可以直接点开，用手机迅雷 App 的「远程设备」投到 NAS）；
- 记录写入 `var/tmb.sqlite3` 的 `downloads` 表，状态 `failed`；
- 面板「最近投递」能看到。

比较常见的拒绝原因：

| 现象 | 原因 |
| --- | --- |
| `invalid token`（纯文本，不是 JSON，HTTP 还是 200） | 飞牛网关在拦登录 Cookie，**不是**迅雷云在拒绝 pan_auth。新版飞牛要 `fnwg_token` + `ost`，且见到 `fnos-token` 就整条拒。**下方有专门一节** |
| `parent folder not found` | 「下载目录 id」对不上：换设备 / 重装迅雷 / 目录被删 / 把路径填进了 id。**下方有专门一节** |
| 只有一串数字（如 `error_code: 9126`） | 迅雷没给文字说明，只回了个码。公开能查到的码会照实翻译，查不到的（9126 属于这类）按「可能是目录问题」自动重试。**下方有专门一节** |
| `refresh token not found` / `device_space_not_active` | 迅雷未登录 / 令牌过期 / 容器重启后空间未激活 |
| 任务创建成功但 `phase=PHASE_TYPE_PENDING` 且速度为 0 | 触发了迅雷「同时下载任务数」上限，排队中（不是失败） |
| 直接报版权 / 任务被拒 | 迅雷侧策略拒绝 |
| `task_create_count_limit`（HTTP 403，`error_code: 11`，「任务创建次数达到上限」） | 迅雷账号侧的建任务额度用完了：非会员有每日任务数上限，短时间内连续投递也会撞上。**不是令牌问题、也不是目录问题**，等额度恢复（通常几十分钟，跨天重置）或换 aria2/qBittorrent 兜底。**下方有专门一节** |

调试建议：面板把日志级别调到 `DEBUG`，再点「重连并诊断」，`xProbeOut` 里会打印原始响应片段，可据此判断是鉴权问题还是参数问题。

## `invalid token` 怎么修

这是最常撞到的一条。迅雷鉴权失败时**不回 JSON**，body 就是一行 `invalid token`，
所以旧版本的报错是 `迅雷拒绝任务: {"_raw_text": "invalid token"}` —— 说了等于没说。

现在它会先判断是哪个令牌，并把结论直接写进错误里：

1.0.42 起不再靠「带不带 Cookie 比回答」猜，而是拿 `<网关>/` 套件首页当探针——
**那个页面不需要 `pan_auth`，打得开就说明登录 Cookie 是好的**：

| `culprit` | 探针结果 | 真实原因 | 怎么修 |
| --- | --- | --- | --- |
| `pan_auth` | 首页 200 拿到 HTML | 登录 Cookie 没问题，是迅雷那条 `pan_auth` 被云端作废了 | 程序会自动从首页把新令牌读回来重试；仍失败就点「立即重连」 |
| `fnos_token` | 同样只回 `invalid token` | 飞牛登录 Cookie 不行（新版要 `fnwg_token` + `ost`，且**不能**带 `fnos-token`） | 从飞牛桌面点开一次面板，或 F12 复制整条 Cookie 粘到设置页 |
| `token_ok` | — | 读列表通了，被拒的是「建任务」这一步 | 先重抓 `pan_auth`，再换磁力排除资源本身；要看报文把日志级别改成 DEBUG |
| （空） | 探针请求本身失败 | 网络 / 端口问题 | 先查端口与路由，别怪令牌 |
| 任意 | `refresh token not found` | 迅雷账号没登录 | 打开迅雷套件扫码登录 |

**先做这一步**：点「重连并诊断」，返回里 `auth` 字段会直接写 `token` 或 `account`，
`culprit` 会指出责任方，`token_age` 告诉你手上这串令牌存了多久，`hint` 就是上面表格里的那句话。命令行等价：

```bash
python3 /var/apps/tgmagnet/target/main.py --probe xunlei
```

### 为什么它老是说「fnos-token 失效」，重登飞牛也没用

因为 1.0.10 及之前是**按模式**判的：网关模式下只要迅雷回一句 `invalid token`，就一律怪 `fnos-token`。
可这句其实是迅雷自己回的，真正过期的往往是 `pan_auth`——飞牛那边早就放行了。
于是形成死循环：重登飞牛 → 还是同样的报错 → 再重登。

1.0.11 改成**实测对比**（`culprit`）：拿同一个接口（`/drive/v1/tasks`）问两次，一次带 `fnos-token`、一次不带：

| 两次的结果 | 结论 |
| --- | --- |
| 带着能读到任务列表 | `token_ok`：令牌没问题，问题在别处，不赖任何一个 |
| 带着失败、去掉反而通 | `drop_token`：这个网关不校验它，把这串清空即可 |
| 两次都一样，且是 `invalid token` 这类迅雷原话 | `pan_auth`：网关压根不看这个 Cookie（本机访问通常免校验），拒绝来自迅雷云 |
| 两次都一样，且是 401 / 登录页 / 「需要登录」 | `fnos_token`：网关自己把人挡住了，Cookie 确实失效 |
| 回答变了（变成要登录/报错不同） | `pan_auth`：网关认了这个 Cookie，问题在迅雷自己的令牌 |

只有对比做不成（网关整个不通、超时）时才会退回「大概率是 fnos-token」的猜测，并且会附上令牌的时间戳。

1.0.11 的对比只做到「两次一样 = 这个 Cookie 没起作用」，然后顺手把它当成了元凶——
其实「没起作用」恰恰说明不该怪它。本机（`127.0.0.1`）访问飞牛网关通常不校验 Cookie，
那时 `invalid token` 只可能来自迅雷云的 `pan_auth`。1.0.16 改成按**错误文本**分流：
迅雷原话归 `pan_auth`，网关侧的 401 / 登录页才归 `fnos_token`。

### 1.0.42：这两条路都判反过一次

2026-11-14 的真实现场：迅雷一直登录着、没退出过，`pan_auth` 的 `exp` 还写着 2 天，
程序却天天 `invalid token`。逐项剥离后真相很朴素——**那句 `invalid token` 根本不是迅雷云说的，
是飞牛网关在拒绝 `fnos-token` 这个名字**（新版改成认 `fnwg_token` + `ost`）。
所以「带不带都是同一句」只能推出「这个 Cookie 没被接受」，推不出「问题在 pan_auth」。
同一条 URL 在浏览器里能用、去掉 Cookie 就 `invalid token`，就是最直接的对照。

教训：**拿一个不需要 `pan_auth` 的地址（套件首页）做探针，比比较两次任务列表的回复可靠得多。**

### pan_auth 什么时候过期，它自己写着

`pan_auth` 是个 JWT，payload 是明文 base64，不用密钥就能读——里面有签发和过期时间。
1.0.16 起「重连并诊断」直接把它解出来摆在一行：

```
迅雷令牌　已于 5 小时前过期　← 就是它
```

或者：

```
迅雷令牌　还有 3 天后到期
```

先看这一行再动手：写「已过期」就去迅雷套件里重新登录（掉登录时任何 `pan_auth` 都无效）；
写「还有 N 天」说明令牌没问题，别在令牌上耗时间，转去看下载目录、设备空间、资源本身。
投递失败的报错里也会带这句。

### 会自动续期吗

**不会自己续**，但能自动「接住」迅雷续好的那个。

`pan_auth` 是迅雷账号的会话令牌，续期这个动作握在迅雷手里——续期要么由迅雷套件在它自己
那边完成，要么得重新登录迅雷账号。程序这边既没有你的迅雷密码，也没有可调的刷新接口，
凭空变不出新令牌。所以「自动续期」这句只能是假的，真话是：

* **迅雷套件一直在线**（大多数人就是这样）→ 它会自己把会话续上、把新 `pan_auth` 写进自己的
  配置或浏览器 Cookie；程序在剩不到 48 小时时，每 6 小时从本机捞一次，捞到的令牌过期时间
  更晚就自动写进配置，并在投递成功的回复里注明「已换用本机找到的令牌」；
* **迅雷那边已经掉登录**（长时间没打开、账号在别处退出、风控）→ 谁也捞不到新令牌，
  程序只能提前提醒：剩不到 72 小时，面板顶栏会出现一个可点的胶囊

  ```
  迅雷令牌 还有 2 天后到期
  ```

  点它会立刻再试一次本机重抓；抓不到就照原话告诉你「本机没有更新的令牌」。日志里也会留一条
  WARNING，事件列表里记一条，同一条令牌只提醒一次，不会刷屏；
* **真过期了** → 投递报 `invalid token`，此时才需要人动手：飞牛桌面 → 迅雷套件 → 确认账号
  仍在线（掉登录就重新扫码）→ 回面板点「立即重连」。

三个窗口都可调（`download.xunlei.*`）：

| 配置 | 默认 | 含义 |
| --- | --- | --- |
| `token_warn_hours` | 72 | 剩这么多小时开始提醒 |
| `token_watch_hours` | 48 | 剩这么多小时开始尝试本机换新 |
| `token_retry_hours` | 6 | 换不到时隔这么久再试 |

想彻底关掉自动动作，把 `auto_refresh_token` 设成 `false`（提醒也会一起停）。

一句话：**剩 2 天不用管**——只要迅雷套件在跑，它续期后程序会自己接住；接不住时，面板会提前
三天挂出提示，而不是等你投递失败了才说。

### 读得通、建任务却被拒：这条报错该怎么读

网关模式下 `culprit=token_ok` 说明**令牌这一步是通的**，被拒的是同一轮投递里的 `POST /drive/v1/task`。
读任务列表在很多版本里问的是飞牛本机的任务库，建任务才真的把请求转给迅雷云端，所以「读得通」推不出「云端令牌有效」：

1. 先点「立即重连」重抓一次 `pan_auth`（只抓它，飞牛不用重登）；
2. 换个磁力投一次：也失败 → 账号/空间/风控；能成功 → 原来那条资源被迅雷拒（下架、无源、敏感）；
3. 两头都正常还报错 → 看原始报文，见下。

**原始响应在哪儿看**：投递被拒时 INFO 级别就会在日志里留一条
`迅雷建任务被拒（目录:xxx）HTTP 200 原始响应：{...}`；把设置里「日志级别」改成 `DEBUG`
（或配置 `app.log_level`）后，每次请求的 URL、请求体、状态码、响应体全文都会打出来，形如：

```
DEBUG [tmb.xunlei] 迅雷请求 → POST http://192.168.1.2:5666/cgi/.../drive/v1/task?pan_auth=ABCD***56 令牌:带 体:{...}
DEBUG [tmb.xunlei] 迅雷响应 ← POST http://... HTTP 200 体:{"error":"invalid token"}
```

日志里的 `pan_auth` / `fnos-token` / 磁力哈希都已经打码（前 4 位 + `***` + 后 2 位），
可以直接整段贴出来求助，不会把令牌一起漏出去。查完记得把级别调回 `INFO`，否则日志涨得很快。

### 报错里夹着乱码 / 一段「二进制」

```
（服务端原话：�       ���1K A ���˫�Ӡ�V� ZY�,��p.��,��" �C* ...）
```

这不是迅雷在骂人，是**压缩过的响应被当文本读了**：网关压了正文却漏回 `Content-Encoding`，
客户端拿到的就是压缩流，按 UTF-8 解码自然全是 `�`。这种响应里往往正好藏着真正的失败原因。

1.0.14 起三层处理：

1. 请求**不再主动要压缩**（`Accept-Encoding: identity`），从源头避开这个坑；
2. 万一还是压缩流，先按 `Content-Encoding` 解；头缺失就按字节特征（`1f 8b` = gzip、`78` = zlib）兜底解；
3. 实在解不出文本（真是二进制）就如实说「回的是二进制内容」，并把原始字节前 120 字节以 hex 记进日志，
   不再把乱码塞进 Telegram；乱码里凑出来的数字也不再当错误码。

另外补了 GBK 回退：迅雷有版本回中文用 GB18030，按 UTF-8 解同样是一屏乱码。

再遇到就翻日志找这一行，把它发出来即可判断：

```
WARNING [tmb.xunlei] 迅雷回了一段非文本响应（312 字节，开头 hex=1f8b0800...）
```

`hex` 以 `1f8b` 开头是 gzip、`78` 是 zlib（理论上都能解）；都不是，说明网关动了别的封装。

### HTTP 400：网关不接受请求体

400 跟令牌无关，通常就是字段缺失或类型不对。1.0.14 的报错会把这次发了哪些字段列出来：

```
网关不接受这个请求体（HTTP 400）：多半是缺必填字段或字段类型不对，换令牌、换目录都没用。
本次发了 file_name,file_size,name,params,space,type；params 里有 url,target,total_file_count。……
```

看到这个就别再重抓令牌了，把这条连同日志里的原始响应一起发出来，按真实字段要求改。

### 令牌明明是好的：最简参数重试

磁力能解析出来，就说明 `pan_auth` 对迅雷云端**是有效的**（解析这一步必须问云端）。
这时候还回 `invalid token`，多半是请求体里某个可选字段这个版本不认——`mime_type`、
`sub_file_index`、`file_size` 都踩过雷。

这时程序会自动再发一次**精简字段**的请求：砍掉 `mime_type` 和 `sub_file_index`
（这两个各版本认法最不一致），其余照留。1.0.13 一开始砍得更狠，把 `file_name` 也删了，
结果网关直接回 400——连真正的错误都问不出来，1.0.14 已纠正。

成功时回复里写「已改用最简请求参数投递成功」。不想要这个兜底，把
`download.xunlei.auto_minimal_body` 设成 `false`。

### 代理、Clash、WireGuard 会不会影响

基本不会，而且现在能自查：

* 程序对内网 / 保留地址**强制直连**，不走代理（相当于给这些地址配了 `NO_PROXY`）；
* 1.0.13 补上了 `100.64.0.0/10`（RFC 6598 CGNAT）——WireGuard、Tailscale 默认就用这一段，
  之前 Python 不把它算私网，请求会被丢给 Clash，反而连不上家里的 NAS；
* 「重连并诊断」的结果多了一行「线路」：
  `直连（目标是内网/保留地址，强制直连、忽略代理）` 或
  `经代理 127.0.0.1:7890（目标是公网地址，按配置经代理）`；失败时若确实走了代理，
  建议里会额外点一句，免得你去瞎改令牌；
* 用 DDNS 域名访问 NAS 时一定算公网地址，会走代理：要么改成局域网 IP，
  要么在 Clash 里给它加一条 `DIRECT` 规则；
* 代理出问题的表现通常是**超时 / 连接被拒**，不会精准地在「建任务」这一步回 `invalid token`。
  看到鉴权类报错时，先别怀疑代理。

想确认线路，在 NAS 上跑一次：

```bash
python3 /var/apps/tgmagnet/target/main.py --probe xunlei | head -20
```

看 `"route"` 那一段：`local: true` 就是直连，`proxy` 非空说明这条请求真的过了代理。

### 在手机飞牛 App 里点，和电脑浏览器有区别吗

**没有区别，手机能做的电脑能做，反之亦然——不用特地回电脑。**

原因是「连迅雷」这件事全程发生在 NAS 内部：点「重连并诊断」或概览的「立即重连」时，是**面板的后台进程**
去请求本机的 `127.0.0.1:5666/cgi/ThirdParty/xunlei/index.cgi`（官方套件网关；
端口由自动侦测确定），手机、电脑、平板都只是发指令的**遥控器**。所以你在手机上点，效果和电脑上一模一样；
同理 Telegram 机器人投递也不经过浏览器，手机发消息、关掉电脑网页都不影响。

唯一的差别是飞牛登录 Cookie 的来源——1.0.42 起抓的是 `fnwg_token` + `ost` 那一组，
从**打开面板那个客户端的 Cookie** 里读：

| 从哪打开 | 会不会带飞牛的登录态 | 面板「令牌来源」显示 |
| --- | --- | --- |
| 飞牛桌面（电脑浏览器） | 带 | 浏览器当前登录态 |
| 飞牛 App 里的应用入口 | 多数会带（App 内也是走网关） | 浏览器当前登录态 |
| 直接输 `http://192.168.1.2:8470/` | 不带 | 配置（上次存下的） |

「没读到浏览器登录态」不代表用不了：只要配置里已经存着一条能用的 Cookie，投递照常。
这句话只影响「想再抓一次新的 Cookie」这一件事——那种情况从飞牛桌面进一次就行。

真要说手机上不方便，只有一种：迅雷套件还没登录过账号，需要打开飞牛桌面里的迅雷套件手动登录。
这一步手机上也能做（飞牛 App 里点开迅雷），只是输账号密码麻烦；而 1.0.17 起令牌会自己扫描续期，
正常情况下不用再手抄。

手机打不开 `8470` 的话：先确认手机和 NAS 在同一个局域网，再用手机浏览器直接输 `http://NAS的IP:8470/`；
面板监听的是 `0.0.0.0`，默认不限制来源。

### 手机 App、电脑网页来回切，会互相踢掉登录态吗

不会。飞牛的登录态是「每端一份」：手机 App 一份、浏览器一份，各自独立，正常地看、点、下任务互不影响；
迅雷账号本身也允许多端同时在线（面板、手机迅雷、网页版并存）。

会互相影响的是这几件事，遇到「忽然又鉴权失败」先回想有没有做过：

* 在**面板来源的那个浏览器**里点了「退出登录」或改了飞牛密码 → 存在配置里的 `fnos-token` 当场作废；
* 飞牛「登录设备管理」里把某台设备下线、或系统升级后旧会话被清；
* 迅雷侧：在迅雷 App 里退出登录、在迅雷「设备管理」里删掉设备、或账号在新设备上重新授权 → `pan_auth` 换新；
* 同一个浏览器切了另一个飞牛账号。

只要这两类都没发生，多端来回看不用担惊——而且它也不会表现成「读得通、写不通」：
会话真被踢掉时连 `/drive/v1/tasks` 都读不出来，那时报的是 `fnos_token` 而不是 `token_ok`。

### 自动重抓

投递时撞到鉴权失败，程序会**在本机重扫一次迅雷**（就是「自动侦测」那套逻辑），
捞到可用令牌就写回配置、立刻重试同一个任务，成功时回复里会标注「本次令牌已自动更新」。

重扫时会把手上的几串候选令牌**都试一遍**——浏览器刚送进来的、配置里存的、从磁盘捞到的，
第一个打通的算数。所以「配置里是几天前的旧值、浏览器送来的是新的」这种最常见的情况，
不用你手动去改配置：它自己会挑对的那串，并在报告里写「换了一串备用令牌才打通」。

三道保险，避免帮倒忙：

* 只在本机重扫（迅雷装在同一台 NAS 上才有意义），最多花两三秒；
* 重扫没拿到 `state=ok` 的候选就**不动配置**，宁可报错；
* 捞到的令牌与现有配置完全一致时不再重试，避免白打一次请求。

不想让它自动动手，把「令牌失效时自动重抓并重试」关掉（`download.xunlei.auto_refresh_token`）。

## `task_create_count_limit` 怎么修（建任务次数达到上限）

现场长这样（HTTP 403）：

```json
{"error":"task_create_count_limit","error_code":11,
 "error_description":"任务创建次数达到上限","HttpStatus":403}
```

这是**迅雷账号侧的额度**，不是你的配置坏了：

* NAS 版迅雷的非会员有**每日任务数上限**；
* 短时间内连续投递（连着发好几条消息、或同一条反复重试）也会撞上这个限制。

1.0.37 起程序把它和「令牌失效」分开判：报错会直说「任务创建次数达到上限」，
并**一次都不重试**——不换目录、不减字段、不去重扫令牌，因为每试一次都在扣同一份额度。
旧版本会把它当鉴权失败，于是同一条磁力对着 403 撞三到四次，额度越用越少。

该做的：

* 等额度恢复（通常几十分钟；**跨天一定重置**），再把那条消息发一次；
* 急着下：手机迅雷 App 里手动加这条磁力（面板「最近投递」能复制原始链接）；
* 长期方案：`download.fallback` 里配 aria2 或 qBittorrent，迅雷没额度时自动由它们接；
* 或者开迅雷会员（额度更宽）。

## `parent folder not found` 怎么修

迅雷要的是**目录 id**，不是目录路径；而且这个 id 只属于当前设备空间。以下任一情况都会让旧 id 失效：

* 换了下载设备 / 重装迅雷 / 容器重建（空间 id 变了）；
* 那个目录在迅雷里被删掉或改名；
* 面板里「下载目录 id」填的是 `/vol1/1000/Downloads` 这种路径（这一步本地就能判出来，不会真发请求去撞）。

报错会被翻成这样（不再是 `迅雷拒绝任务: {"_raw_text": "parent folder not found"}`）：

```
迅雷下载目录无效：下载目录 id 在当前迅雷里对不上（换设备、重装迅雷、目录被删，
或把路径当成 id 填进去都会这样）。两种改法：把「下载目录 id」留空＝投到迅雷默认目录；
要指定目录，在迅雷面板文件列表里选中目录，从地址栏的 parent_folder_id= 后面复制那串 id
（服务端原话：parent folder not found）
```

两种改法，二选一：

1. **留空**（推荐）：面板「下载目录 id」清空，任务落到迅雷默认下载目录，之后在迅雷里随便挪。
2. **填对 id**：打开迅雷面板 → 文件 → 点进目标目录 → 复制地址栏里 `parent_folder_id=` 后面那一串。
   换过设备的话，务必从**当前设备**的文件列表里复制。

### 三级尝试：默认目录 → 迅雷用过的目录

默认开着「目录 id 无效时改用默认目录」（`download.xunlei.auto_fallback_folder`）。
投递被拒时按下面顺序再试，任何一步成功就停：

1. 按你填的目录 id 投（填了才走这步）；
2. **去掉目录参数再投一次** —— 让下载先落到迅雷默认目录；
3. **用「迅雷自己用过的目录」再投一次** —— 从任务列表里捞 `parent_folder_id`，
   那是迅雷亲口承认能用的 id，比自己手抄靠谱。

成功时 Telegram 回复会写明用的是哪一种：

```
已投递迅雷（1 个文件）· 本次用的是已有任务里的下载目录：/vol1/1000/Downloads（已把这个目录写进设置，下次直接用）
```

**注意：不再自动改你的设置。** 1.0.9 曾经在降级成功后把「无效的目录 id」清空，
可能把还能用的配置删了——这一版只在**投递成功**时把「刚刚被迅雷接受的那个目录」
写进配置；失败时一个字都不动，只提示「建议到面板把下载目录 id 清空或改成实际目录」。

关掉这个开关（`auto_fallback_folder: false`）就退回硬失败：宁可报错，也不让文件落到你没指定的目录。

另一种情况：**你根本没填目录 id，迅雷还是回这句**。那说明它连默认目录都找不到（迅雷里没有可写目录，
或换过设备空间还没准备好），改 id 没用。程序会把话换成「迅雷没找到可用的下载目录：本次用的是默认目录
（没指定 id）也被拒……」，让你先去看迅雷面板里到底有没有文件列表。

## 只回一个数字错误码（如 `9126`）怎么办

把「下载目录 id」清空之后，迅雷有时不再回 `parent folder not found`，而是只丢一个数字，
比如 `error_code: 9126`。这类 4 位新码官方**没有公开对照表**，程序不猜它的含义，
而是做三件事：

1. **能查到的码照实翻译**（来源：迅雷远程下载帮助页 / 社区）：

   | 错误码 | 含义 | 处理 |
   | --- | --- | --- |
   | `2` | 远程调用失败 | 迅雷设备空间反向代理超时，刚启动或网络抖动，重试 |
   | `107` | 创建文件或写数据失败 | 目录不存在或没写权限 |
   | `108` / `112` | 磁盘空间不足 | 清理下载盘或换目录 |
   | `131` | 服务器连接异常 | 迅雷服务端临时故障，等几分钟 |
   | `202` | 任务已存在 | 这条资源已经在迅雷里了 |

2. **查不到的码按「可能是目录问题」处理**：依次试「默认目录 → 迅雷用过的目录」，
   不少情况下任务就这样投进去了，你不用管 9126 到底是什么意思。

3. **都不行才报错**，并且把话说清楚：

```
迅雷拒绝了任务（错误码 9126），它没给文字说明，只回了码。常见三类原因：
① 下载目录不存在或不可写；② 设备空间刚换过、还没准备好；③ 这条资源被迅雷侧策略拒绝。
先打开迅雷面板手动新建一条任务试试，能成就是本程序参数的问题，不能成是迅雷那边的问题。
```

### 找回下载目录

面板迅雷卡片上的「从已有任务找下载目录」按钮，会读迅雷任务列表里它自己写过的
`parent_folder_id` / `parent_folder_path`，列出来并把第一条写进设置。命令行等价：

```bash
python3 /var/apps/tgmagnet/target/main.py --xunlei-folder           # 只看候选
python3 /var/apps/tgmagnet/target/main.py --xunlei-folder --apply   # 把第一条写进配置
```

`--probe xunlei` 的返回里也会带 `folders` 字段，就是这些候选。
